## Verdict — issues to fix before merge

### ❌ Critical (release blockers)

1. **Leak #13 — wrong-tenant policy resolution: NO defense in code.** The integration plan claims "Auth policy re-evaluated at privilege change". Zero artifact found across `backend/`. The brainstorming explicitly mapped this to paused tasks #89–92 (per-org password/verification on `feature/per-org-auth-policy`); that branch has not been integrated. **Fix:** either land the per-org auth-policy work or rewrite the plan to acknowledge #13 is deferred to Phase 6+.

2. **Leak #15 — per-tenant rate limit: not wired.** `TenantRateLimiterSet` exists and is tested, but `host_tenant_middleware` contains only `// SEAM(leak#15)` comments — no `.check().await`, no 429 path, no caller in `servers/`. operability.md acknowledges the gap; the integration-plan checklist must reflect it. **Fix:** wire `TenantRateLimiterSet::check()` into `host_tenant_middleware` after `ResolvedTenant` is injected, return 429 on `DenyTooManyRequests`, write an integration test that exhausts a single tenant's quota and confirms an OTHER tenant still succeeds.

3. **Leak #19 — per-tenant metering: not wired.** Same shape as #15. `meter_request()` exists but is never called. operability.md acknowledges the gap. **Fix:** wrap `next.run(request).await` to extract response size and call `meter_request(org_id, bytes)` after every resolved-tenant request.

### ⚠️ Weak (must address before "done")

4. **Leak #16 — soft-delete RLS filter: zero integration tests.** Migration 00140 rewrites every tenant policy to AND `get_current_org_not_deleted()`. There is **no test in `crates/db/tests/` or `tests/integration/`** that sets a tenant context, sets `deleted_at`, and asserts zero rows. A regression in the generator script silently ships. **Fix:** add a `soft_delete_filter_hides_tenant_rows` test in `rls_smoke_tests.rs` covering at least 3 representative tables (own_org, child via FK, listings with the 4-context policy).

5. **Leak #20 — TenantedRedis: zero callers.** Wrapper is correct; no live code uses it. The `no-raw-redis.sh` lint protects future code but does not retro-fix the existing reality-server / integrations Redis usage. **Fix:** identify every current `RedisClient::set/get` call site (operability.md says this is "Phase 5 work" — has not been done), replace with `TenantedRedis`, then trim the lint allowlist.

6. **Leak #21 — RequireCapability still trusts JWT role claim.** `crates/admin-core/src/extractor.rs:113` calls `auth.is_platform_admin()` which reads the JWT-claim `role` — the same claim Phase 2 says is untrustworthy. The "single mechanism" requirement (invariant I-C) is not satisfied while two divergent admin checks coexist. **Fix:** the extractor must derive `principal_kind` from `users.principal_kind` (mirror `RequestPrincipal`'s logic) before the capability lookup; then the JWT-role claim can finally be removed from token issuance per the integration plan §"Cleanup".

7. **Leak #21 — no-self-grant has no test.** `capability.rs:292-295` rejects `user_id == granted_by`. No test exercises this path. A regression would silently ship. **Fix:** add `grant_rejects_self_grant` to `capability_gate_tests.rs` (one-liner using the existing `YesGrants` fixture).

8. **Leak #21 — `PrincipalKindEscalate` granter-holds-it check is documented but missing.** `capability.rs:185-186` and `:11` claim the granter must already hold `PrincipalKindEscalate` to grant it. Code-side: not implemented in `PgCapabilityGrantsRepository::grant`. **Fix:** either implement the check in `grant()` or remove the docstring claim.

9. **Leak #21 — tenant lifecycle routes bypass capability gate.** `routes/admin_tenant_lifecycle.rs:200-209` (`require_platform_admin`) checks `is_platform_admin()` only. The most destructive endpoints (export, purge, restore) do **not** require `Capability::TenantPurge` etc., do not require recent MFA, and do not write a capability-audit row. **Fix:** swap `require_platform_admin(&auth)` for `RequireCapability(Capability::TenantPurge)` (etc.) — the capability constants already exist in `crates/admin-core/src/capability.rs:88-90`.

10. **Leak #12 — `set_principal_kind` HTTP route is a 501 stub.** `routes/admin/users.rs:116-127` returns `NOT_IMPLEMENTED` and the TODO comment is the live escalation path. Today an operator needing to mint a `platform` principal must run psql directly, which bypasses the audit row and the principal_kind_change leak guard's user-context. **Fix:** call `SELECT set_principal_kind($1, $2, $3, $4)` from the handler; the SECURITY DEFINER function and audit are already wired.

11. **Leak #3 — cache invalidation only on CREATE.** `tenant_resolution_cache.invalidate(host)` is called in exactly one place (agency_provisioning.rs:296). No domain-release endpoint exists — but if/when one lands, the brainstorming's "treat removal as a security event" requirement won't be enforced unless this is paired in the same change. **Fix:** when a domain-delete or `verification_state -> revoked` mutation is added (likely Phase 6), insert the invalidation call alongside.

### Bonus — leaks discovered from cross-phase composition

12. **`AuthUser` vs `RequestPrincipal` split is the real "skeleton key" risk in this branch.** Phase 2 introduces `RequestPrincipal` (correct). Phase 5's `RequireCapability` still uses the legacy `AuthUser` (incorrect). Therefore: a token whose `role` claim was minted as `super_admin` in the legacy issuance path will pass Phase 5's `is_platform_admin()` check AT THE EXTRACTOR LEVEL even after the user has been demoted in the DB via `set_principal_kind('staff')`. The capability lookup in step 3 may save us only because `capability_grants` rows are super-admin-RLS — but the audit-denial row at step 2 is for the wrong reason and doesn't catch the underlying token-trust problem. **The composed system has a smaller hole than #21 on its own; the fix is cross-phase.**

13. **Phase 5.5 admin routes bypass Phase 5 gate (already enumerated as #9 above)** — flagging it again here because the integration plan's leak→phase table marks #21 as defended in Phase 5; the lifecycle-routes hole is a Phase 5 / Phase 5.5 composition gap, not a single-phase failure.

## Summary

- Defenses scored: **9 ✅ · 7 ⚠️ · 3 ❌** (out of the 22 leaks).
- **Phase 1 + Phase 2 defenses are the strongest** — host resolution, RLS connection discipline, principal_kind guard, token scope all check out with end-to-end tests.
- **Phase 5.5 has a systematic gap**: every "wire it into the middleware" defense (#15 rate limit, #19 metering, #20 tenanted Redis usage) ships as a typed primitive only. operability.md acknowledges this; the INTEGRATION-PLAN.md checklist does not.
- **Phase 5 has a systematic gap too**: the capability gate trusts JWT claims in step 2, has no test for no-self-grant, and is bypassed entirely by the Phase 5.5 lifecycle routes.
- **#13 has zero defense at all** and depends on a parked branch.
