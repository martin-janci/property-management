# Endpoint Checklist — api-server + reality-server (BIT-247)

Authoritative, test-verified classification of **every HTTP endpoint** in both backend
servers. Generated by a deterministic, reproducible audit of `origin/dev`
(`backend/servers/api-server/src/routes/**` and `backend/servers/reality-server/src/routes/**`),
cross-referenced against the `tests/*.rs` suites. See [`_SPEC.md`](./_SPEC.md) for the
exact method and taxonomy; per-domain detail is in [`groups/`](./groups).

> Snapshot: `origin/dev` @ `684d7f68c` · 2026-06-27 · 208 route source files. Updated through BIT-256 (58 stubs → done).

## Headline numbers

There are **two different questions** the board is really asking, and they have very
different answers. Read both.

| Metric | Count | % of all endpoints |
|---|---|---|
| **DONE** — real handler **and** a passing happy-path test | **165** | **8.0%** |
| Partial — real handler, **no** happy-path test | 1808 | 87.6% |
| Stub — handler missing/mock/`501`/unmounted | 90 | 4.4% |
| Missing — in spec/use-case, no handler | 0 | 0.0% ✓ confirmed by BIT-269 |
| **Total endpoints** | **2063** | 100% |

- **Test-verified DONE = 8.0%.** This is the strict number the ticket defines: an
  endpoint only counts as done if a test exercises its success path. By that bar the
  platform is ~8% done.
- **Implementation breadth = 95.6%** (`done + partial`). Almost every endpoint has a
  real, DB/repo-backed handler. Only **4.4% are stubs/mock/unmounted**.

**The gap is test coverage, not implementation.** The overwhelming majority of the
codebase's tests are **authorization / cross-org IDOR / RBAC rejection** suites that
assert `401/403/404` and deliberately never reach a `2xx`. They harden the security
boundary (which is the right first priority) but they do not prove the feature works,
so they cannot promote an endpoint to `done`. Closing the 8.0% → high-90s gap is
primarily a **happy-path integration-test** effort, not a build effort (BIT-256 closed 58 stubs: +23 migration, +19 regional_compliance, +14 data_residency, +2 OCR).

## Current vs. future state

**Current state.** The API surface is broad and largely built: 1973 of 2063 endpoints
(95.6%) have real handlers. Security posture is the most-tested dimension. 8.0% of
endpoints have a test that proves the feature actually works end-to-end. The previously
mock-returning compliance modules (`regional_compliance`, `data_residency`) are now
DB-backed (BIT-256).

**Roadmap to a high test-verified % (grouped, in priority order):**

1. **De-risk the remaining mocks (3 endpoints).** `compliance.rs` gdpr/data-exports,
   `rentals.rs` id-document/extract, and reality `agency_imports` test-connection still
   return stub/fabricated data. *High priority — correctness/compliance risk.*
2. **Happy-path coverage for the high-traffic core (~1000 endpoints).** faults,
   finance, governance, org-property, admin-platform, analytics are ~100%-implemented
   but ~2-4% tested. Add success-path integration tests group-by-group. This is the
   single biggest lever on the headline number and is **test work, not build work**.
   Blocker to retire first: several suites note the auth harness "can't mint a tenant_id
   JWT," which is why so many tests call repos directly instead of issuing HTTP requests
   — fixing the JWT test fixture unblocks happy-path testing across many groups.
3. **Decide the fate of unmounted scaffolds (87 endpoints).** For `public_api` /
   `integrations/sync` / `vendor_portal`: either commit to the epic (add migrations,
   mount, implement, test) or delete the scaffold. Keeping unmounted `501` code inflates
   the surface and confuses audits.
4. **AI/automation (93 endpoints, 2.2% tested).** Two OCR endpoints now done (BIT-256);
   91 partial handlers need a dedicated happy-path test pass.

## Caveats / method notes

- No local Rust toolchain on the audit host, so coverage is determined by **static
  cross-reference** (test files hit endpoints by URI string, e.g. `.uri("/api/v1/...")`).
  This is deterministic and reproducible but conservative: a test that exercises a path
  without a clear `2xx` assertion is treated as **not** proving the success path.
- Several test files exercise the **repository layer directly** rather than the HTTP
  endpoint (noted per group). Those do not count toward `done` for the endpoint.
- A handful of routers are **dead code** (defined but never mounted, e.g.
  `signatures::document_signature_router`) — excluded from counts and flagged in group
  notes.
- Endpoint counts treat each `(method, path)` pair as one endpoint; dual-mounted
  routers (e.g. `market_pricing` at `/pricing` + `/market-pricing`) are counted once.
- **`Missing=0` caveat resolved (BIT-269).** A spec→handler diff (`scripts/diff_endpoints_v3.py`)
  surfaced 65 apparent gaps in the OpenAPI spec vs. mounted handlers. All 65 were
  confirmed to be **path/method divergences** between a stale spec snapshot and the
  settled implementation (e.g. `/votes` → `/voting`, flat `/units` → nested under
  `/buildings/{id}/units`, `PATCH` → `PUT` throughout, `/reservations` → `/bookings`).
  No operation in the spec or use-case catalog lacks a mounted handler. See
  [`_SPEC_DIFF.md`](./_SPEC_DIFF.md) for the full breakdown.
